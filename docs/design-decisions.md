# 設計判断

採った案と、そのときに退けた案を残す。
コードを読めば「どうなっているか」は分かるが、「なぜそうなっていないか」は分からない。
同じ論点に二度向き合わずに済むよう、判断の理由をここに置く。

## 例外の置き場所を層ごとに分ける

業務ルールに反する操作は Domain 層の例外が表す。
「貸出中の書籍は貸し出せない」という判断は `Book` 自身が下し、HTTP の知識を持たない。

操作の前提となる対象が無いことは、Application 層の例外が表す。
対象の不在は、ある操作を始められるかどうかの話であって、書籍という概念の性質ではない。

要求の形の検証は Adapter 層に置く。
「題名が文字列か」は形の問題で、「その書籍を貸し出せるか」は業務の問題である。
同じ場所に置くと、形の規則と業務の規則が混ざり、どちらを直せばよいかが読み取れなくなる。

分けた結果、状態番号の割り当ては層の対応で決まる。
Adapter 層の例外が `400`、Application 層の例外が `404`、Domain 層の例外が `409` になる。

## 見つからないことを例外にしない

Repository は、対象が無いときに例外を投げず `null` を返す。

一覧の取得では0件が正常な結果であり、識別子での取得では対象の不在が誤りである。
この2つを同じ例外で表すと、呼び出し側は「空の棚」と「間違った棚番号」を区別できない。
`null` を返して、区別の判断を呼び出し側に残す。

## 蔵書の一覧に貸出を添える

`GET /books` は、各書籍に `currentLoan` を添えて返す。
返却されていない貸出があれば借り主と貸出日と返却期限が入り、無ければ `null` になる。

添えないと、呼び出し側は一覧を取ってから書籍の数だけ貸出を問い合わせることになる。
12冊の蔵書を表示するために13回の往復が必要になり、表示のたびに増える。

## 返却期限の超過を業務ルールとして持たない

返却期限を過ぎているかどうかは、返却期限と現在時刻から画面側で判定する。
Domain 層の `Loan` は、超過しているかを答えない。

超過が貸出の可否や督促に影響する要件は、まだ無い。
影響しないものを業務ルールとして持つと、要件が現れたときに、既にある判定を読み直してから設計することになる。
要件が決まったときに Domain 層へ移す。

## 画面と API をワークスペースの下に並べる

リポジトリ直下を npm のワークスペースにし、`apps/api` と `apps/web` を並べた。

API だけを直下に残して画面を `apps/web` に置くと、階層が非対称になる。
「`src` は API の `src`、画面は `apps/web` の下」という説明を、読み手に毎回させることになる。

## 画面の意匠を Mantine の既定のままにする

色、余白、角丸、文字の大きさ、太さ、行間は、すべて Mantine 9 の既定を使う。
独自のテーマファイルは置かない。
Mantine に対応する目盛りが無い骨格の寸法（トップバーの高さ、詳細列の幅、列の間隔）だけを `apps/web/src/styles/tokens.css` に集める。

手書きの部品も置かない。
一覧は `Table`、絞り込みは `SegmentedControl`、状態の表示は `Badge`、割合の円は `RingProgress`、読み込み中の仮表示は `Skeleton` を使う。

既定から離れるほど、部品を1つ足すたびに「この画面ではどの色か、どの余白か」を先に決めることになる。
決めた結果はどこにも書かれないので、次に足す人は既存の画面から読み取るしかない。
既定のままなら、その判断が発生しない。

## 絞り込みにサイドバーを使わない

状態の絞り込みは3つしかない。
280ピクセルの列を丸ごと使う量ではないので、`SegmentedControl` を一覧の見出しの横に1行で置く。

`SegmentedControl` なら、状態の名前と該当する冊数が常に文字で見える。
名前と公開リポジトリへのリンクは、高さ56ピクセルのトップバーが持つ。

## 書籍の詳細を右の列に出す

行を押すと、右の列が全体の状況からその書籍の詳細に切り替わる。
行の下に詳細を差し込む形は採らない。

題名と状態と登録日と識別子と貸出の窓口を並べる量になると、開いた行が下の行を押し下げる。
押した行より下が視界から消え、一覧を見ながら詳細を読むという目的が崩れる。

選んだ書籍は URL の検索引数に持たせる。
画面をそのまま共有でき、再読み込みしても同じ書籍が開く。

ただし読み込みの依存には入れない。
入れると、行を選ぶたびに蔵書の一覧の再取得が走る。
絞り込みを変えたときと、指された識別子が一覧に無いときは、選択を外す。

## 対応するデータが無い要素を画面に置かない

意匠の案にあっても、API が返さない値は画面に出さない。
貸出の履歴、返却の予定、利用者ごとの統計は、いずれも今の API に無いので置かない。

押しても動かない要素があると、読み手は動かない理由を探すことになる。
動く要素だけを置けば、画面に見えているものがそのまま API の能力になる。

## ユーザーを作る窓口を画面に置かない

ユーザーは `npm run db:seed` が4件用意する。
画面からは作れない。

載せると、貸出を試すまでに「ユーザーを作る、書籍を登録する、貸し出す」の3手が必要になる。
この画面で見せたいのは貸出と返却の流れなので、その手前の手数を減らす。
ユーザーを作る経路は `POST /users` として API 側にあり、消えたわけではない。

## 開発中だけ `/api` を転送する

画面からの要求はすべて `/api` の下に出す。
Vite の開発サーバーが `http://localhost:3000` へ転送し、そのときに `/api` を取り除く。

画面のコードは、自分と同じ生成元だけを見ればよくなる。
API の待ち受けポートを画面側が知る必要がなく、生成元をまたぐ要求の設定も要らない。
