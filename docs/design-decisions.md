# 設計判断

採った案と、そのときに退けた案を残す。
コードを読めば「どうなっているか」は分かるが、「なぜそうなっていないか」は分からない。
同じ論点に二度向き合わずに済むよう、判断の理由をここに置く。

## 例外の置き場所を層ごとに分ける

業務ルールに反する操作は Domain 層の例外が表す。
「貸出中の本は貸し出せない」という判断は `Book` 自身が下し、HTTP の知識を持たない。

操作の前提となる対象が無いことは、Application 層の例外が表す。
対象の不在は、ある操作を始められるかどうかの話であって、本という概念の性質ではない。

要求の形の検証は Adapter 層に置く。
「題名が文字列か」は形の問題で、「その本を貸し出せるか」は業務の問題である。
同じ場所に置くと、形の規則と業務の規則が混ざり、どちらを直せばよいかが読み取れなくなる。

分けた結果、状態番号の割り当ては層の対応で決まる。
Adapter 層の例外が `400`、Application 層の例外が `404`、Domain 層の例外が `409` になる。

## 見つからないことを例外にしない

Repository は、対象が無いときに例外を投げず `null` を返す。

一覧の取得では0件が正常な結果であり、識別子での取得では対象の不在が誤りである。
この2つを同じ例外で表すと、呼び出し側は「空の棚」と「間違った棚番号」を区別できない。
`null` を返して、区別の判断を呼び出し側に残す。

## 本の一覧に貸出を添える

`GET /books` は、各本に `currentLoan` を添えて返す。
返却されていない貸出があれば借り主と貸出日と返却期限が入り、無ければ `null` になる。

添えないと、呼び出し側は一覧を取ってから本の数だけ貸出を問い合わせることになる。
40冊を表示するために41回の往復が必要になり、表示のたびに増える。

## 返却期限の超過を業務ルールとして持たない

返却期限を過ぎているかどうかは、返却期限と現在時刻から画面側で判定する。
Domain 層の `Loan` は、超過しているかを答えない。

超過が貸出の可否や督促に影響する要件は、まだ無い。
影響しないものを業務ルールとして持つと、要件が現れたときに、既にある判定を読み直してから設計することになる。
要件が決まったときに Domain 層へ移す。

## 画面と API をワークスペースの下に並べる

リポジトリ直下を npm のワークスペースにし、`apps/api` と `apps/web` を並べた。

API だけを直下に残して画面を `apps/web` に置くと、階層が非対称になる。
「`src` は API の `src`、画面は `apps/web` の下」という説明を、読み手に毎回させることになる。

## 色は意味ごとに1組だけ持つ

画面が使う色は4組しかない。
藍が貸出中、朱が返却期限の超過、緑が返却、墨が文字と貸出可を表す。
値は `apps/web/src/theme.ts` に置き、Mantine の色として登録する。

Mantine の既定の青・赤・緑をそのまま使うと、どの画面でも同じ色になる。
色が何も語らないので、何を扱うサービスなのかは文字を読むまで分からない。

朱は、超過している貸出があるときだけ画面に出る。
いつ見ても出ている色は、出ていること自体が合図にならない。

色以外の目盛り（大きさ、太さ、行間、余白、角丸）は Mantine の変数をそのまま使う。
`apps/web/src/styles/tokens.css` が持つのは、書体と、Mantine に対応する目盛りが無い骨格の寸法だけである。
同じ寸法を2か所に書くと、どちらが効いているかを読み手が確かめられなくなる。

## 本の題名だけを明朝で組む

書体は3つを役割で使い分ける。
本の題名が明朝、ラベルとボタンと説明がゴシック、日数と日付と識別子が等幅である。

日本の本の題名は明朝で組まれる。
その約束事に合わせると、一覧の中で題名だけが本の見た目を持つ。

等幅は桁をそろえるために使う。
返却期限と残りの日数は行をまたいで比べるものなので、桁がずれると読み比べに目の移動が要る。

装飾として明朝を置くことはしない。
見出しやサービス名まで明朝にすると題名との区別が消え、書体が役割を表さなくなる。

## 返却予定を画面の上段に出す

貸出中の本を返却期限の近い順に並べ、本の一覧より上に置く。
超過しているものは期限が最も古いので、並べるだけで先頭に出る。

貸出では、何もしなくても時間が進んで状態が悪くなる。
放置しても変わらない冊数より、放置すると超過になる期限のほうが先に目に入るべきである。

1枚ごとに、期限までの日数と、貸出期間のどこまで来たかを表す帯を出す。
帯の長さは貸出日と返却期限の差から計算する。
期間の日数を画面に書くと、返却期限を決める業務ルールが `Loan` と画面の2か所に現れる。

この表示に必要な値は `GET /books` の応答にすべて含まれる。
期限だけを返す経路は足さない。

## 絞り込みにサイドバーを使わない

状態の絞り込みは3つしかない。
280ピクセルの列を丸ごと使う量ではないので、`SegmentedControl` を一覧の見出しの横に1行で置く。

`SegmentedControl` なら、状態の名前と該当する冊数が常に文字で見える。
サービスの名前と全体の件数は画面上部の見出しが持ち、公開リポジトリへのリンクは末尾に置く。

## 本の詳細を右の列に出す

行を押すと、右の列が登録の窓口からその本の詳細に切り替わる。
行の下に詳細を差し込む形は採らない。

題名と状態と登録日と識別子と貸出の窓口を並べる量になると、開いた行が下の行を押し下げる。
押した行より下が視界から消え、一覧を見ながら詳細を読むという目的が崩れる。

選んだ本は URL の検索引数に持たせる。
画面をそのまま共有でき、再読み込みしても同じ本が開く。

ただし読み込みの依存には入れない。
入れると、行を選ぶたびに本の一覧の再取得が走る。
絞り込みを変えたときと、指された識別子が一覧に無いときは、選択を外す。

## 対応するデータが無い要素を画面に置かない

意匠の案にあっても、API が返さない値は画面に出さない。
過去の貸出の履歴、貸出の予約、ユーザーごとの統計は、いずれも今の API に無いので置かない。

押しても動かない要素があると、読み手は動かない理由を探すことになる。
動く要素だけを置けば、画面に見えているものがそのまま API の能力になる。

## ユーザーを作る窓口を画面に置かない

ユーザーは `npm run db:seed` が4件用意する。
画面からは作れない。

載せると、貸出を試すまでに「ユーザーを作る、本を登録する、貸し出す」の3手が必要になる。
この画面で見せたいのは貸出と返却の流れなので、その手前の手数を減らす。
ユーザーを作る経路は `POST /users` として API 側にあり、消えたわけではない。

## 開発中だけ `/api` を転送する

画面からの要求はすべて `/api` の下に出す。
Vite の開発サーバーが `http://localhost:3000` へ転送し、そのときに `/api` を取り除く。

画面のコードは、自分と同じ生成元だけを見ればよくなる。
API の待ち受けポートを画面側が知る必要がなく、生成元をまたぐ要求の設定も要らない。
